# outou-cli

The `outou` command: `build`, `check`, `cargo`, `fmt` and `package`. `outou package` generates Rust and includes it in the published crate so that consumers need only `cargo build`.

Phase 0: Weeks 4–6.

The binary (`src/main.rs`) is a thin argument-parsing wrapper. The actual `build` pipeline is a library (`src/lib.rs`, `pub mod build`), so `cargo xtask determinism` and this crate's own tests can call it directly without spawning the `outou` process — "there is one compiler" (`AGENTS.md`).

## `outou build`

```
outou build [--manifest-dir DIR]
```

Resolves the module graph at `DIR` (default: the current directory) with `outou-modules`, generates Rust for every `ModuleGraph::generated_units()` node with `outou-backend-dioxus`, and writes each one under `src/.generated/` per ADR 0009 layout (b), plus a `<name>.rs.map.json` source map next to it (the spike-compatible JSON form, `SourceMap::to_json`, written to disk at `version: 1` with its `generated`/`sources` fields rewritten to crate-relative paths — `build::paths::relativize_map_json`; the v1 schema already documents those fields as "a path or URI", so this needs no format bump). The generated `.rs` header (`// Generated by Outou from <path>. Do not edit.`) also names its source with a crate-relative path (`outou_codegen::GenerateOptions::source_display`), never the generating machine's own absolute path (ADR 0008 consequences): two checkouts of the same `.rsx` sources at two different absolute locations always regenerate byte-identical output, which is what makes `cargo xtask determinism` and `outou package --check` (below) able to compare raw bytes with no normalization step. Files are written atomically (temporary file, then rename), and any managed file (`*.rs`, `*.rs.map.json`) left over from a module that was renamed or removed is deleted; anything else under `src/.generated/` is left alone.

- No `.rsx` crate root (`src/main.rsx`/`src/lib.rsx`) — including a crate with only a plain `.rs` root — prints a message and exits `0`: there is nothing to do.
- Both a `.rsx` root and its `.rs` counterpart existing side by side is an error.
- `outou build` always runs in Strict mode; there is no `--mode` flag. `cargo build` can never tolerate a syntax error, so any Outou syntax error is a build failure, reported with Outou's own rendered diagnostics (`outou_syntax::render`) — never backend vocabulary (`rsx!`, `PropsBuilder`, `dioxus_rsx`, `GeneratedNode`, `dioxus`). Recovery mode remains available directly through `outou_cli::build::emit::generate_unit` for callers that need it (`outou-lsp`, which depends on this crate's library for exactly that reuse, and `cargo xtask determinism`'s independent second code path).

**Permanent rule (issue #8, accepted in issue #24):** a plain Rust (`.rs`) file may not declare a `.rsx` child module (`mod y;` in `src/x.rs`, where `y.rsx` exists). Codegen only ever rewrites a `mod` declaration's `#[path]` inside a *generated* file (a `.rsx` file's own output); it never touches a `.rs` file's source, so there is no way to point such a declaration at `y`'s generated output. `outou build` detects this shape while planning (a `SourceKind::Rust` module graph node with a non-inline `SourceKind::Rsx` child) and reports it as an Outou diagnostic: `` module `y` is declared from the plain Rust file `src/x.rs`; `.rsx` modules must be declared from `.rsx` files or from the crate root ``. `.rsx` modules must be declared from another `.rsx` file, or from the crate root itself. `tests/fixtures/modules/{rs-to-rsx,path-attr}` (built for `outou-modules`' resolver) both contain this exact shape and are the fixtures `crates/outou-cli/src/build/plan.rs`'s own tests check the error against; they are intentionally excluded from the build-pipeline integration suite (`tests/build_paths.rs`), which only builds supported shapes.

### Workspace support (issue #10)

`--manifest-dir` may also point at a Cargo *workspace* root (a manifest with a `[workspace]` table and no `[package]` table): `outou_cli::build::workspace::workspace_members` reads its `members`/`exclude` lists with the `toml` crate (`cargo_metadata` was deliberately not pulled in, to keep `outou build` from spawning `cargo` itself) and `build()` recurses into each member in turn, merging their `Report`s. A manifest carrying both `[package]` and an empty `[workspace]` table (`examples/phase0-app`'s own shape, only used to opt out of the repository's workspace) still builds as the single crate it is — `[package]`'s presence always wins over recursing into zero members. `exclude` removes a path `members` would otherwise include (even one a `/*` glob just expanded to); the resolved member list is deduplicated (issue #12 corpus review, F10); a `[workspace]` table that resolves to zero members after `exclude` is a clear error (`WorkspaceError::NoMembers`), not a silent "nothing to do".

**Permanent behavior (accepted in issue #24):** member-path globbing is limited to a single trailing `/*` segment on one path component (`"crates/*"`); `tests/fixtures/workspace`'s own root `Cargo.toml` lists members by full path instead. Any other glob character (`"crates/**"`, bracket patterns, `?`) is refused with an explicit error that asks for the member paths to be listed, instead of being treated as a literal path (which used to end in an operating-system error). The exception is a directory that really is named with such a character (`lit/q?x`, `crates/foo*`) and holds a `Cargo.toml`: it is that literal member, as in Cargo. `[workspace] default-members` is not read: `outou build` and `outou cargo` always cover every member (the `--workspace` behavior), and that key could only ever narrow it — see `workspace_members`'s own doc comment.

## `outou check`

Parses every `.rsx` file under the current crate's `src/` directory (recursively, in sorted order — a dot-directory such as `src/.generated/` is never descended into, and a symlink is never followed) with `outou_syntax::parse` — the same front end `build`'s generation step and the language server use — and prints Outou's own rendered diagnostics for any file that has one: `error: <message>` for an error-severity diagnostic, `warning: <message>` for a warning-severity one, each followed by ` --> <path>:<line>:<col>`. Exits `1` if any file has an error-severity diagnostic, `0` otherwise (warnings alone do not fail the check). When no file has an error it prints one summary line (`outou check: checked N `.rsx` files, no errors`, or `no `.rsx` files found under `src``), so a clean run is distinguishable from a run that checked nothing (dogfood friction F16).

`outou build` and `outou cargo` print the same warning-severity diagnostics (`warning: <message>` then ` --> <path>:<line>:<col>`) to standard error before anything else, on every run (also when no file is rewritten), and they never change the exit code. Paths are relative to the current directory when the file is below it, else absolute. The build stops at the first unit with a syntax error, so warnings of earlier units are not shown then (`outou check` shows everything). `outou cargo -q` and `-p` do not scope warnings (they cover the whole crate or workspace, like generation). `outou package` does not print warnings.

`outou check` is **syntax only**: it never runs the Rust compiler, so type errors, borrow errors and lints are not found. Use `outou cargo check` for those.

## `outou cargo` (issue #25, ledger row 39)

```
outou cargo <build|check|clippy|test> [cargo args...]
```

`outou cargo check` is `outou build` followed by `cargo check`, with the compiler's diagnostics reported at the `.rsx` line and column instead of at `src/.generated/<file>.rs`:

```
error[E0308]: mismatched types
  --> app/src/task_list.rsx:39:22
   |
39 |     let wrong: u32 = "oops";
   |                      ^^^^^^ expected `u32`, found `&str`
   = note: expected due to this (app/src/task_list.rsx:39:16)
```

1. It generates Rust for the crate (or workspace) in the current directory, or the one holding `--manifest-path`, exactly like `outou build`: always Strict, so an Outou syntax error stops here in Outou's own words and Cargo never runs.
2. It runs `$CARGO` (else `cargo`) `<sub> --message-format=json-diagnostic-rendered-ansi <args>`. `RUSTC_WORKSPACE_WRAPPER` is not used: clippy ignores it. The JSON stream is the one interface `build`, `check`, `clippy` and `test` share.
3. Each `compiler-message` line is translated (below) and printed to **standard error**. Every other line of Cargo's standard output is test output: lines that are not a JSON object with a `reason` key pass through to **standard output** byte for byte, and Cargo's own records (`compiler-artifact`, `build-script-executed`, `build-finished`) are not printed. Only those four `reason`s are Cargo's: a line with any other `reason` is the program's. After `build-finished`, every line is the program's output, however much it looks like a Cargo record (`outou cargo test -- --nocapture` can print JSON of its own). Cargo's own standard error (`Compiling ...`, `error: could not compile`) is inherited.
4. The exit code is Cargo's; when a signal ended Cargo (Unix) it is `128 + N`, like a shell reports. A refused command line exits `2`; a generation failure exits `1`.

Everything after the subcommand goes to Cargo unchanged, including `--` (`outou cargo clippy -- -D warnings`, `outou cargo test -- --nocapture`). Two flags are refused before anything is generated or run, when they appear before `--`:

- `--fix`: a fix would rewrite `src/.generated/`, which the next `outou build` overwrites. Edit the `.rsx` file.
- `--message-format` (either spelling): `outou cargo` needs the JSON form to find the spans. It fails with a clear message instead of silently picking one of the two. Run `cargo` directly when another format is wanted.

A toolchain override (`cargo +nightly ...`) cannot be given, since the first argument is the subcommand: use `RUSTUP_TOOLCHAIN=nightly outou cargo check`. `TODO(alpha) (#31)`: Windows is out of scope for the alpha (CI and the documentation target Unix), and path handling for `C:\...` file names in rustc's prose is not implemented.

`outou cargo` differs from `outou check` in what it runs: `check` parses `.rsx` files and never starts the compiler; `outou cargo check` runs the Rust compiler on the generated code.

### What is translated, and what is not

The translation lives in `outou_cli::diagnostics` and is shared with the UI test harness (`tests/ui.rs`): "there is one compiler". The rules, in order:

1. **A generated file with a source map** (`<file>.rs.map.json` next to it): the primary span is mapped to the `.rsx` file, line and column. The same narrowing `outou-lsp` uses is applied first (`SourceMap::narrow`), then the whole-span answer, then the nearest mapped position.
2. **A span of 15 or more lines** (rustc reports the whole `rsx!` call for some errors) is first narrowed as a whole: when it narrows exactly (a long closure inside a spliced Rust run) the range is kept, carets and all. Otherwise it is mapped by its start only, so the diagnostic points at the start of the nearest element or statement; no range is invented.
3. **A synthesized span with no mapping** (the `child(..)` call generated around a child expression) uses the nearest mapped position rather than dropping a hard error.
4. **Secondary spans** (`expected due to this`) are shown as notes only when they map exactly into a `.rsx` file. A span that carries a macro expansion points at the backend's macro (`expansion.def_site_span` names a file in the Cargo registry) and is always dropped. So is a `note:` / `help:` child that has a span in a file outside the workspace (an absolute path: a registry dependency, the standard library) or from a macro expansion (`method defined here`, `required by a bound in ...`), and the pair of notes that say a long type name was written to a file in the build directory.
5. **A suggested replacement** (clippy's `help: try`) is shown as `replace `old` with `new` (file:L:C)` (`insert `new`` when the original text is empty) only when the generated text under the span is byte for byte the `.rsx` text it maps to. Otherwise the help message is kept without the replacement.
6. **A plain `.rs` file** (`src/.generated/../state.rs`, a module reached through `#[path]`) needs no map. Its path is normalised and rustc's own rendering is printed (colour only when standard error is a terminal and `NO_COLOR` is unset), but only when that rendering is safe: it names no registry or dependency path, has no span from a macro expansion and no backend vocabulary. Otherwise `outou cargo` renders the diagnostic itself, from the workspace spans only.
7. **A generated file whose map cannot be read** keeps the message and drops the location, so no `.generated` path is ever printed.
8. **Backend vocabulary** in a message is rewritten by `outou_syntax::vocabulary::translate_message` (the table `outou-lsp` uses). A label or note that would need rewriting is dropped, since it repeats the message. The backend vocabulary scan of `tests/leak.rs` covers this output.
9. **An untranslated twin** of a translated missing-prop diagnostic (ledger row 27) is dropped: only the `this method takes N argument` error whose label names a `Missing_required_field` type, and only at the same generated byte range as an already shown translated diagnostic. Another diagnostic that merely maps to the same `.rsx` span (a `#[deprecated]` warning on the component) is kept. The batch (UI harness) and the stream (`outou cargo`) are one implementation; both rely on rustc reporting the translated one first, and a twin without it is shown rather than lost. The `Some errors have detailed explanations: ...` and `For more information ...` notes then list only the codes that were shown.
10. **Text that names the generated directory** (a closure type `{closure@src/.generated/x.rs:15:14: 15:22}`, `` couldn't read `src/.generated/x.txt` ``) is cleaned in every message, label and note: a position in generated code is mapped to the `.rsx` position (`<generated code>` when it cannot be); a bare path shows as `<generated directory>/x.txt`, with a note that relative paths in `include_str!` resolve from the generated Rust's directory (ledger row 40).
11. **The trait helps around a JSX child diagnostic** (``cannot be rendered as a JSX child``, issue #27): rustc's ``the trait `Iterator` is not implemented for ...`` describes the facade's implementation, not the mistake, and is dropped (for a `Vec` it becomes ``a `Vec` is not an iterator; use `.into_iter()` (or `.iter()`) to render its items``). Under every message, a note or help that names `IntoChild<..>` (the list of implementing types, ``required for `Option<usize>` to implement `IntoChild<outou::jsx::Delegated<_>>` ``) is dropped. rustc's `Result<VNode, RenderError>` is named `Element` in a child diagnostic, so ``Vec<Element>`` keeps its message. The facade's own notes (what a child can be, `if` / `Option` for a condition, `.map(|n| n.to_string())`) stay.

Not translated: output of the program under test (a panic's `src/.generated/x.rs:33:5`, a backtrace), because it is not a compiler message; and plain `cargo` itself, which still prints generated paths (use `outou cargo`). `outou cargo` generates only the crate or workspace it is run in, like `outou build`.

## `outou package` (issue #15)

```
outou package [--manifest-dir DIR] [--check] [-- <cargo package args>]
```

`outou package` always operates on exactly one library crate, the one at `--manifest-dir`; it never iterates a workspace's members on its own. Pointing it at a workspace root (a manifest with `[workspace]` and no `[package]`) fails immediately with an error naming it as a workspace root — pass `--manifest-dir <member>` once per member that publishes instead. (An application member's `src/.generated/` is gitignored by design, so silently walking every member would report spurious drift for it.)

`--check`: runs only `package::check_generated` — plans the crate, generates every unit in memory (always Strict, the same mode `outou build` uses) and compares the result against what is actually on disk under `src/.generated/`, reporting three kinds of drift (`changed`, `missing`, `stale` — a managed file the current plan does not produce at all) without writing anything or invoking `cargo`. A clean crate prints `outou package --check: generated output is up to date` and exits `0`; any drift lists every affected file (crate-relative paths, not the checkout's own absolute ones — location-independent CI logs) and exits `1`. This is what the `generated-drift` CI job runs against every committed, `outou`-generated fixture.

Without `--check`: runs `build::build` to regenerate (exactly like `outou build`), then confirms every generated `.rs` file `outou build` just wrote is actually included in `cargo package --list`'s output for the crate — a gitignored `src/.generated/`, or a `[package] include` that does not name it, would otherwise silently publish a library with no generated Rust at all, defeating the entire point of ADR 0008. A mismatch fails with an actionable message naming the missing file(s) and the two likely causes. A crate with no `.rsx` crate root at all prints `` outou package: no `.rsx` crate root found; nothing to do `` and exits `0` without ever running `cargo package`. Once confirmed, runs `cargo package` (the `$CARGO` binary if set, else `cargo` on `PATH`) with any arguments after `--` passed straight through (e.g. `outou package -- --allow-dirty`), propagating its own exit code.

Passthrough args after `--` are validated before any of this runs: `--manifest-path`, `--workspace`, `--all` and `--exclude` (in any `--flag=value` form) are rejected outright, since they would let `cargo package` select packages `outou package` never verified. `-p`/`--package` is allowed — publishing needs `-- -p outou -p ui-kit`, since `outou` itself is unpublished (below) — but only when the crate at `--manifest-dir` is itself one of the named packages; otherwise `cargo package` could ship an unverified crate while skipping the one `outou package` did check. **Accepted (issue #24):** `outou package` verifies the crate at `--manifest-dir` and nothing else. Any *other* `-p` package named alongside is passed to `cargo` unverified; in practice it is a plain `.rs` crate like the `outou` runtime itself.

**Phase 0 publish blocker, resolved (issue #15):** `outou` itself is not published to crates.io, so a *standalone* `cargo publish --dry-run` of a library like `ui-kit` fails ("no matching package named `outou` found ... crates.io index"). Cargo's own docs note that packaging several inter-dependent crates in one `cargo package`/`publish` invocation builds their lockfile assuming all of them land on the same registry together — exactly this repository's shape, since `outou` and any Outou library are always published together. `crates/outou-cli/tests/matrix.rs`'s `outou_and_ui_kit_publish_dry_run_succeeds_together` (`#[ignore]`d; confirmed first as a manual spike) builds a temp workspace whose only two members are standalone copies of `crates/outou` and `ui-kit`, runs `outou package --manifest-dir ui-kit -- --allow-dirty -p outou -p ui-kit` (checking the `.crate` archive itself actually ships `src/.generated/`), then `cargo publish --dry-run -p outou -p ui-kit` from it — both packages verify and "upload" (the dry run aborts the actual upload), exit `0`. Its negative counterpart, `outou_package_fails_when_generated_output_is_gitignored`, builds the same kind of temp workspace but without `ui-kit`'s `.gitignore` negation, and asserts `outou package` refuses to ship a library with no generated Rust.

## The Cargo command matrix (issue #10)

After `outou build`, the rest of the ordinary Cargo workflow — `cargo build`/`check`/`test`/`clippy`/`package` — is exercised against real generated output, both for an application (`examples/phase0-app`) and for a small workspace of one `.rsx` library and one `.rsx` application (`tests/fixtures/workspace/{ui-kit,app}`; see `crates/outou-cli/tests/matrix.rs`). `cargo build`/`check`/`test`/`clippy --all-targets -- -D warnings` and `cargo package --list` all pass for `examples/phase0-app`; `cargo build`/`test`/`clippy --workspace --all-targets -- -D warnings` and `cargo package --list` (for both members) all pass for the two-crate workspace fixture (`cargo check` is not separately run against the workspace). `cargo publish --dry-run` is not run against that fixture: a standalone `ui-kit` publish cannot resolve the unpublished `outou` (see the "publish blocker, resolved" paragraph above). It passes instead for `outou` and `ui-kit` packaged together in a separate temporary two-crate workspace (`outou_and_ui_kit_publish_dry_run_succeeds_together`). A `.rsx` file's own `#[cfg(test)] mod tests` runs under `cargo test` exactly like a `.rs` file's would, and a plain (JSX-free) `///` doc test on a library function runs under `cargo test --doc` (`tests/fixtures/workspace/ui-kit`'s `add_one`) — codegen copies a function's attributes (including its doc comments) into the generated file verbatim, so this needs no special handling. Two genuine, Cargo-level layout constraints were found along the way, neither one specific to JSX or to the Dioxus backend:

- **A `[[bin]]`-only crate cannot run any doc test, plain or JSX.** `cargo test --doc` refuses outright with "no library targets found in package `<name>`" before it even looks at individual doc comments, because a doc test is compiled linking against the crate as a library (`rlib`), which a binary target never produces. `examples/phase0-app` is `[[bin]]`-only by design (ADR 0009's application layout), so its own plain doc test on `components::initial` (added for this issue) cannot run there — recorded, not worked around: adding a `[lib]` target pointing at the same generated `crate-root.rs` compiles (and clippy-fails, since `AGENTS.md` forbids `allow`) on an unused private `fn main()`, once that file is also compiled as a library. A real Outou application wanting doc-tested `.rsx` helpers needs a library + thin binary crate, exactly the shape `tests/fixtures/workspace/{ui-kit,app}` demonstrates.
- **`cargo package -p ui-kit` ships `src/.generated/` with no `[package] include` needed.** `cargo package --list -p ui-kit` lists `src/.generated/crate-root.rs` and every other generated file, because `ui-kit` lives inside this repository's git working tree and the root `.gitignore` negates `**/.generated/` for exactly this path (`!tests/fixtures/workspace/ui-kit/src/.generated/`): Cargo's default packaged-file list for a crate in a git repository is VCS-aware (tracked files, honoring `.gitignore`), so the negated files are treated like any other tracked source. An earlier version of this document claimed Cargo unconditionally drops dot-prefixed paths from a package even with an explicit `include`; that was false, and traced back to how `matrix.rs`'s temp-copy helper worked at the time — copying the fixture into a bare directory with no `.git` at all, which put `cargo package` on its separate "no VCS found" fallback file-listing path, and that fallback path (not the normal git-aware one) is what drops dot-prefixed paths regardless of `include` (cargo 1.98.1). `matrix.rs` now makes its temp copy a real git working tree (with the same `.gitignore` rules as this repository) before packaging, so the check exercises the code path a real `cargo publish` actually uses.
- **The genuine Phase 0 publish limitation — `outou` itself is unpublished — is resolved, not worked around (issue #15).** A *standalone* `cargo publish --dry-run --allow-dirty -p ui-kit` still fails with "no matching package named `outou` found ... location searched: crates.io index", because `ui-kit`'s `outou` dependency is a local `path` dependency (with a `version` requirement alongside it, as `cargo publish` requires) and `outou` has not actually been published to crates.io. But packaging `outou` and `ui-kit` *together*, in one `cargo publish -p outou -p ui-kit` invocation, works: Cargo builds the temporary lockfile for a multi-package publish assuming every packaged crate lands on the same registry together, so `ui-kit`'s `path` dependency on the `outou` being packaged alongside it resolves. See `outou package`'s own section above and `outou_and_ui_kit_publish_dry_run_succeeds_together` in `tests/matrix.rs`.
