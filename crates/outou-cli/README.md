# outou-cli

The `outou` command: `build`, `check` and `package`. `outou package` generates Rust and includes it in the published crate so that consumers need only `cargo build`.

Phase 0: Weeks 4–6.

The binary (`src/main.rs`) is a thin argument-parsing wrapper. The actual `build` pipeline is a library (`src/lib.rs`, `pub mod build`), so `cargo xtask determinism` and this crate's own tests can call it directly without spawning the `outou` process — "there is one compiler" (`AGENTS.md`).

## `outou build`

```
outou build [--manifest-dir DIR]
```

Resolves the module graph at `DIR` (default: the current directory) with `outou-modules`, generates Rust for every `ModuleGraph::generated_units()` node with `outou-backend-dioxus`, and writes each one under `src/.generated/` per ADR 0009 layout (b), plus a `<name>.rs.map.json` source map next to it (the spike-compatible JSON form, `SourceMap::to_json`; `generated`/`sources` are `file://` + absolute path — `cargo xtask determinism` normalizes this prefix away before comparing). Files are written atomically (temporary file, then rename), and any managed file (`*.rs`, `*.rs.map.json`) left over from a module that was renamed or removed is deleted; anything else under `src/.generated/` is left alone.

- No `.rsx` crate root (`src/main.rsx`/`src/lib.rsx`) — including a crate with only a plain `.rs` root — prints a message and exits `0`: there is nothing to do.
- Both a `.rsx` root and its `.rs` counterpart existing side by side is an error.
- `outou build` always runs in Strict mode; there is no `--mode` flag. `cargo build` can never tolerate a syntax error, so any Outou syntax error is a build failure, reported with Outou's own rendered diagnostics (`outou_syntax::render`) — never backend vocabulary (`rsx!`, `PropsBuilder`, `dioxus_rsx`, `GeneratedNode`, `dioxus`). Recovery mode remains available directly through `outou_cli::build::emit::generate_unit` for callers that need it (`outou-lsp`, which depends on this crate's library for exactly that reuse, and `cargo xtask determinism`'s independent second code path).

**Phase 0 limitation (`TODO(phase0)`, issue #8):** a plain Rust (`.rs`) file may not declare a `.rsx` child module (`mod y;` in `src/x.rs`, where `y.rsx` exists). Codegen only ever rewrites a `mod` declaration's `#[path]` inside a *generated* file (a `.rsx` file's own output); it never touches a `.rs` file's source, so there is no way to point such a declaration at `y`'s generated output. `outou build` detects this shape while planning (a `SourceKind::Rust` module graph node with a non-inline `SourceKind::Rsx` child) and reports it as an Outou diagnostic: `` module `y` is declared from the plain Rust file `src/x.rs`; Phase 0 requires `.rsx` modules to be declared from `.rsx` files or from the crate root ``. `.rsx` modules must be declared from another `.rsx` file, or from the crate root itself. `tests/fixtures/modules/{rs-to-rsx,path-attr}` (built for `outou-modules`' resolver) both contain this exact shape and are the fixtures `crates/outou-cli/src/build/plan.rs`'s own tests check the error against; they are intentionally excluded from the build-pipeline integration suite (`tests/build_paths.rs`), which only builds shapes Phase 0 supports.

### Workspace support (issue #10)

`--manifest-dir` may also point at a Cargo *workspace* root (a manifest with a `[workspace]` table and no `[package]` table): `outou_cli::build::workspace::workspace_members` reads its `members`/`exclude` lists with the `toml` crate (`cargo_metadata` was deliberately not pulled in, to keep `outou build` from spawning `cargo` itself) and `build()` recurses into each member in turn, merging their `Report`s. A manifest carrying both `[package]` and an empty `[workspace]` table (`examples/phase0-app`'s own shape, only used to opt out of the repository's workspace) still builds as the single crate it is — `[package]`'s presence always wins over recursing into zero members. `exclude` removes a path `members` would otherwise include (even one a `/*` glob just expanded to); the resolved member list is deduplicated (issue #12 corpus review, F10); a `[workspace]` table that resolves to zero members after `exclude` is a clear error (`WorkspaceError::NoMembers`), not a silent "nothing to do".

**`TODO(phase0)`:** member-path globbing is limited to a single trailing `/*` segment on one path component (`"crates/*"`), the only shape this repository's fixtures need (`tests/fixtures/workspace`'s own root `Cargo.toml` lists members by full path instead). A richer glob (`"crates/**"`, bracket patterns, …) is out of scope for Phase 0. `[workspace] default-members` is also not read — see `workspace_members`'s own doc comment for why that key alone would only ever *narrow* what `outou build` builds, never the `--workspace`-equivalent behavior it always needs today.

## `outou check`

Parses every `.rsx` file under the current crate's `src/` directory (recursively, in sorted order — a dot-directory such as `src/.generated/` is never descended into, and a symlink is never followed) with `outou_syntax::parse` — the same front end `build`'s generation step and the language server use — and prints Outou's own rendered diagnostics for any file that has one: `error: <message>` for an error-severity diagnostic, `warning: <message>` for a warning-severity one, each followed by ` --> <path>:<line>:<col>`. Exits `1` if any file has an error-severity diagnostic, `0` otherwise (warnings alone do not fail the check). `package` remains `todo!()`; it is a separate piece of Week 6's work from the Cargo command matrix below.

## The Cargo command matrix (issue #10)

After `outou build`, the rest of the ordinary Cargo workflow — `cargo build`/`check`/`test`/`clippy`/`package`/`publish` — is exercised against real generated output, both for an application (`examples/phase0-app`) and for a small workspace of one `.rsx` library and one `.rsx` application (`tests/fixtures/workspace/{ui-kit,app}`; see `crates/outou-cli/tests/matrix.rs`). `cargo build`/`check`/`test`/`clippy --all-targets -- -D warnings` all pass for both; a `.rsx` file's own `#[cfg(test)] mod tests` runs under `cargo test` exactly like a `.rs` file's would, and a plain (JSX-free) `///` doc test on a library function runs under `cargo test --doc` (`tests/fixtures/workspace/ui-kit`'s `add_one`) — codegen copies a function's attributes (including its doc comments) into the generated file verbatim, so this needs no special handling. Two genuine, Cargo-level layout constraints were found along the way, neither one specific to JSX or to the Dioxus backend:

- **A `[[bin]]`-only crate cannot run any doc test, plain or JSX.** `cargo test --doc` refuses outright with "no library targets found in package `<name>`" before it even looks at individual doc comments, because a doc test is compiled linking against the crate as a library (`rlib`), which a binary target never produces. `examples/phase0-app` is `[[bin]]`-only by design (ADR 0009's application layout), so its own plain doc test on `components::initial` (added for this issue) cannot run there — recorded, not worked around: adding a `[lib]` target pointing at the same generated `crate-root.rs` compiles (and clippy-fails, since `AGENTS.md` forbids `allow`) on an unused private `fn main()`, once that file is also compiled as a library. A real Outou application wanting doc-tested `.rsx` helpers needs a library + thin binary crate, exactly the shape `tests/fixtures/workspace/{ui-kit,app}` demonstrates.
- **`cargo package -p ui-kit` ships `src/.generated/` with no `[package] include` needed.** `cargo package --list -p ui-kit` lists `src/.generated/crate-root.rs` and every other generated file, because `ui-kit` lives inside this repository's git working tree and the root `.gitignore` negates `**/.generated/` for exactly this path (`!tests/fixtures/workspace/ui-kit/src/.generated/`): Cargo's default packaged-file list for a crate in a git repository is VCS-aware (tracked files, honoring `.gitignore`), so the negated files are treated like any other tracked source. An earlier version of this document claimed Cargo unconditionally drops dot-prefixed paths from a package even with an explicit `include`; that was false, and traced back to how `matrix.rs`'s temp-copy helper worked at the time — copying the fixture into a bare directory with no `.git` at all, which put `cargo package` on its separate "no VCS found" fallback file-listing path, and that fallback path (not the normal git-aware one) is what drops dot-prefixed paths regardless of `include` (cargo 1.98.1). `matrix.rs` now makes its temp copy a real git working tree (with the same `.gitignore` rules as this repository) before packaging, so the check exercises the code path a real `cargo publish` actually uses.
- **The genuine Phase 0 publish limitation: `outou` itself is unpublished.** `cargo publish --dry-run --allow-dirty -p ui-kit` fails with "no matching package named `outou` found ... location searched: crates.io index", because `ui-kit`'s `outou` dependency is a local `path` dependency (with a `version` requirement alongside it, as `cargo publish` requires) and `outou` has not actually been published to crates.io. ADR 0008 says a consumer of an Outou library needs only `outou`, no build dependency — but the library's own generated code still depends on `outou` (`::outou::__private::*`) as an ordinary dependency, and that dependency has to exist on the registry before the library publishing it can. This is an ordinary Cargo constraint (any crate with an unpublished `path` dependency fails to publish the same way), not a dot-directory or JSX-specific one. `TODO(phase0)`: `outou package`'s real publish story needs to either require `outou` to be published first, or otherwise resolve that dependency at publish time — this is unrelated to ADR 0009's `src/.generated/` layout, which packages just fine.

## Tests

- `tests/build_paths.rs`, `tests/build_cli.rs`, `tests/build_compile.rs` (split out of one `tests/build.rs`, issue #8 fix list step 10; shared temp-directory helpers in `tests/support.rs`): together, build every required build-pipeline fixture (`tests/fixtures/modules/{mixed,cfg,cfg-duplicate,raw-ident,root-name,inline,inline-dup,inline-dup-rs}`) and `examples/phase0-app` through `outou_cli::build::build`, asserting the exact generated file set, `#[path]`/`#[cfg]` fidelity, stale-file cleanup, atomic-write idempotency and transactionality, and (in `build_compile.rs`, mostly `#[ignore]`d — a cold `dioxus` build) that the result actually passes `cargo check`/`cargo test`/`cargo clippy`, including a probe that a user's own redundant braces still fail `cargo clippy -- -D warnings` in a file whose generated code carries no `#![allow(unused_braces)]` (`docs/backend-leakage.md` rows 21, 23). `build_cli.rs` also asserts the `outou` binary itself exits `1` and prints only Outou vocabulary for a `.rsx` syntax error, and rejects the removed `--mode` flag.
- `tests/matrix.rs` (issue #10; no `mod support;` — see the file's own note): the Cargo command matrix described above. `outou_build_builds_every_workspace_member_in_one_pass` and `outou_build_regenerates_ui_kit_generated_output_byte_identically` are fast (no `cargo`/`rustc` invocation) and run as part of the normal suite; `example_app_doc_tests_cannot_run_because_there_is_no_library_target` is fast too (`cargo test --doc` fails at the manifest-check stage, before compiling anything). `example_app_cargo_matrix` and `workspace_fixture_cargo_matrix` are `#[ignore]`d (a cold `dioxus` build, one temp copy and one `outou build` per test, every Cargo command below it reusing that same build) — run explicitly with `cargo test -p outou-cli --test matrix -- --ignored`, wired into CI as the `cargo-matrix` job.
