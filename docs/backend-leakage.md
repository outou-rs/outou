# Backend leakage ledger

Outou uses Dioxus as a temporary execution backend. Every constraint that Dioxus imposes on Outou code is recorded here and classified so that the runtime decision after Phase 0 is made from a list, not from a feeling.

Classifications:

- **Outou intrinsic** — the behavior is part of Outou's own semantics and would exist with any backend.
- **Dioxus leakage** — a Dioxus detail visible to Outou users. Must not become permanent specification.
- **Temporary limitation** — something Outou intends to support but cannot with this backend.
- **Accepted permanent behavior** — a Dioxus behavior Outou has decided to keep on its own merits.

| # | Constraint | Origin | Classification | Notes |
|---|---|---|---|---|
| 1 | Props must be `Clone` | Dioxus `#[component]` / `Props` derive | Dioxus leakage | Not an Outou language rule. Revisit at the runtime decision. |
| 2 | Props must be `'static` | Dioxus component model | Dioxus leakage | Follows from #1 and #9. |
| 3 | Props must be `PartialEq`, and equality drives re-rendering | Dioxus memoization | Dioxus leakage | Outou has not defined its own update semantics yet. |
| 4 | `Element = Option<VNode>` | Dioxus core | Dioxus leakage | Outou exposes the name `Element` only. Whether it stays an `Option` is a runtime decision. |
| 5 | The type of `children` is Dioxus's `Element` | Dioxus | Dioxus leakage | Same as #4. |
| 6 | `#[component]` is lowered to a Dioxus component definition (a props struct plus a function) | Outou marker, Dioxus lowering | Outou intrinsic (marker) / Dioxus leakage (lowering) | The attribute itself is backend-neutral and required in Phase 0. Only the generated shape is Dioxus. |
| 7 | `rsx!` is re-exported through `outou::__private` and appears in generated code | Codegen | Temporary limitation | Hidden path; never written by users. Appearing in a user-facing diagnostic is a Phase 0 failure. |
| 8 | Signals, hooks and their rules (`use_*` ordering, `Signal<T>` API) are Dioxus's | Dioxus | Dioxus leakage | Outou defines no hook or signal of its own in Phase 0. |
| 9 | Event model: handler types, event names and the `on*` attribute convention | Dioxus HTML crate | Dioxus leakage | Outou JSX event syntax is Outou's; the handler types are not. |
| 10 | `&str` (borrowed) props are not supported: `fn Greeting(name: &str) -> Element` does not compile | Dioxus `'static` props | Temporary limitation | Use `String` in Phase 0. Borrowed props are an Outou goal. |
| 11 | Macro expansion names in scope: the backend's macros expand to unhygienic paths, so `outou::prelude` must also bring `dioxus_core`, `dioxus_elements`, `dioxus_signals` and `Props` into scope (hidden from docs) | Dioxus macro hygiene | Dioxus leakage | Discovered while building the facade. These names are visible to completion in user code. Codegen could instead emit fully qualified paths; TODO(phase0) decide at Gate 2. |
| 12 | Element and attribute vocabulary (`div`, `class`, …) is validated by the Dioxus HTML crate | Dioxus HTML crate | Temporary limitation | An unknown attribute produces a Dioxus error today. Outou must translate it (see [design.md](design.md)). |
| 13 | Generated Rust must live at a fixed `src/.generated/` path referenced with `#[path]`, not under Cargo's `OUT_DIR` via `include!()` | rust-analyzer (Week 1 spike, `spikes/rust-analyzer/`) | Temporary limitation | Measured directly: with the identical `rsx!`-macro-based generated code, `OUT_DIR` + `include!()` made rust-analyzer's completion return zero/`null` results inside the `rsx!` macro call and under incomplete/broken input (both work fine for the `#[path]` layout). Not a Dioxus constraint — reproduced with the backend's own macro either way; the difference is an observed rust-analyzer behaviour difference between an `include!()`-spliced file and an ordinary `#[path]` source file; the mechanism was not investigated. See `docs/ra-spike-results.md` and ADR 0009. Outou intended to offer `OUT_DIR` as an option (matching Cargo convention for generated code); that option is dropped as a result. |
| 14 | Attribute keys that are not a plain Rust identifier (hyphenated — `data-id` — or a Rust keyword — `type`, `for`, …; both legal per grammar §5) are emitted with Dioxus's raw string-key attribute syntax (`"data-id": value`) instead of `name: value` | Dioxus `rsx!` macro | Dioxus leakage | `crates/outou-backend-dioxus/src/escape.rs`, `is_plain_ident`. The JSX name itself is Outou intrinsic; the specific workaround syntax for writing it as a field key is Dioxus's. |
| 15 | Attribute and text string values are lowered into Dioxus's own format-string literals (`rsx!`'s ifmt), so a literal `{`/`}` byte in the value must be doubled to `{{`/`}}` before it is safe to splice | Dioxus `rsx!` macro (ifmt) | Dioxus leakage | `crates/outou-backend-dioxus/src/escape.rs`, `rust_string_literal`. Not observable through Outou's own grammar today — a raw `{`/`}` cannot appear inside `JsxText`, since `{` always opens an island (grammar §6) — but constrains codegen's implementation, and would surface immediately if that grammar rule ever changed. |
| 16 | Row 11's `TODO(phase0)` is resolved: codegen cannot emit fully qualified paths (`::dioxus_core::…`) instead of re-exporting `dioxus_core`/`dioxus_elements`/`dioxus_signals`/`Props` into `outou::prelude` | Dioxus `rsx!`/`#[component]` macro expansion | Dioxus leakage | Confirmed by reading the vendored `dioxus-rsx 0.7.10` and `dioxus-core-macro 0.7.10` sources (`~/.cargo/registry/src/*/dioxus-rsx-0.7.10/src/{element,component,template_body}.rs`): every expansion emits bare paths (`dioxus_core::TemplateNode::…`, `dioxus_elements::#i::#name`, `dioxus_core::Properties`, `dioxus_signals::GlobalSignal`), never `::`-prefixed ones, so these names must be in scope wherever `rsx!`/`#[component]` is invoked — i.e. in the user's own generated file, which only imports `use outou::prelude::*;`. Row 11's re-exports (already present in `crates/outou/src/lib.rs`) remain necessary; this row records that the alternative was investigated and rejected, not silently dropped. |
| 17 | Correction to row 14: its raw string-key attribute syntax (`"name": value`) exists only for **elements**. On a **component** it does not compile at all (`error[E0599]: no method named 'push_attribute' found for struct '<Name>PropsBuilder<TypedBuilderFields>'`) | Dioxus `rsx!` macro / derived `Props` struct | Dioxus leakage | Issue #6, HIGH-3. A keyword name (`type`, `for`, …) is therefore instead written as a raw identifier, `r#name: value` — verified to compile for both elements and components — so row 14's workaround now applies, unqualified, only to a hyphenated name and to the four keywords Rust itself refuses as a raw identifier (`self`, `Self`, `crate`, `super`); see row 18 for the hyphenated case on a component specifically. `crates/outou-backend-dioxus/src/escape.rs`, `is_raw_identifiable_keyword`. |
| 18 | A hyphenated JSX attribute name (`data-id`) is unrepresentable on a **component**: it is not a legal plain identifier, and `-` makes it illegal as a raw identifier too (`r#data-id` does not parse), so there is no Rust field-key spelling for it in a derived Props struct at all | Rust identifier grammar, via Dioxus's derived `Props` struct | Dioxus leakage | Issue #6, HIGH-3. Only the element form (row 14's raw string-key syntax) can carry a hyphenated name. Until Outou translates this itself, `<Field data-id="x" />` reaches the user as a `PropsBuilder` compile error — the vocabulary AGENTS.md names as a Phase 0 failure (row 19 records the general version of that failure). No fix applied in issue #6; recorded per the fix list's decision to defer it. |
| 19 | rustc diagnostics for generated code render Dioxus's own type paths and `PropsBuilder` machinery directly to the user, not just backend vocabulary in prose | Dioxus component model (`#[component]`/`Props` derive) surfacing through `rustc`'s own path-printing and deprecation lints | Dioxus leakage | Issue #6, HIGH-6. `#[doc(hidden)]` is rustdoc-only and does not change how `rustc` prints a path; `outou::prelude::dioxus_core` is a genuinely public path and the shortest one available, so rustc chooses it. Reproduced in a plain user crate: a non-`IntoDynNode` island child gives `` the trait bound i32: IntoDynNode<outou::prelude::dioxus_core::nodes::FromNodeIterator> is not satisfied ``; a missing required prop gives `` warning: use of deprecated method `GreetingPropsBuilder::<((),)>::build`: Missing required field name `` together with `` argument #1 of type `GreetingPropsBuilder_Error_Missing_required_field_name` is missing `` and `` this error originates in the derive macro `Props` ``. Not fixable by removing the re-export (rustc would print `dioxus_core::…` instead); inherent to using Dioxus as a backend. Row 11 records only that the names are visible to completion; row 16 records only that qualified paths are impossible. Neither records diagnostics rendering them, which is the more consequential fact. |
| 20 | A non-`String`/`&str`/`Element`/iterator island child does not compile: Dioxus requires a child's type to implement `IntoDynNode` | Dioxus core (`IntoDynNode`) | Temporary limitation | Issue #6, HIGH-7. `<p>{n}</p>` with `n: i32` fails with `error[E0277]: the trait bound i32: IntoDynNode<…> is not satisfied`; `{n.to_string()}` compiles. React allows a bare number (or `null`/`bool`, which React renders as nothing) as a child; Outou does not yet translate this restriction into an Outou diagnostic. Row 12 covers element/attribute vocabulary, not island child types. |
| 21 | An island attribute value (`attr={expr}`) is always wrapped in braces when lowered (`attr: {expr}`), which trips Rust's own `unused_braces` lint in the user's build (`<div tabindex={1}>`, `onclick={move \|_\| …}`, …), pointing into `src/.generated/` | Codegen (`crates/outou-backend-dioxus/src/element.rs`, `lower_island`) | Temporary limitation | Issue #6, MEDIUM-12. Not universally strippable: dropping the braces breaks a nested-`rsx!` island prop (`icon={<span/>}` needs them — `error: expected identifier` without); replacing them with parens produces `unused_parens` instead. A `-D warnings` user's build fails on this today. No fix applied in issue #6 (no clean universal fix exists); deferred to issue #8. |
| 22 | Correction to row 15: a literal `{`/`}` byte **is** observable through Outou's own grammar today, in an attribute string value — `class="a{b}c"` is legal Outou and hits exactly the ifmt-escaping row 15 describes. Only the `JsxText` (element child text) half of row 15's claim holds, since `{` always opens an island there (grammar §6) | (documentation correction; no code change) | Dioxus leakage | Issue #6, LOW-16. Row 15 itself is not rewritten (rows are appended, never rewritten); this row narrows its scope to the half that is actually true. |

Rows are appended, never rewritten, as new leakage is found. The runtime decision after Phase 0 counts how many rows make Outou semantics unnatural and weighs that against interop freedom, renderer control, performance, bundle size, API stability and upgrade cost.
