# Backend leakage ledger

Outou uses Dioxus as a temporary execution backend. Every constraint that Dioxus imposes on Outou code is recorded here and classified so that the runtime decision after Phase 0 is made from a list, not from a feeling.

Classifications:

- **Outou intrinsic** — the behavior is part of Outou's own semantics and would exist with any backend.
- **Dioxus leakage** — a Dioxus detail visible to Outou users. Must not become permanent specification.
- **Temporary limitation** — something Outou intends to support but cannot with this backend.
- **Accepted permanent behavior** — a Dioxus behavior Outou has decided to keep on its own merits.

| # | Constraint | Origin | Classification | Notes |

| 2 | Props must be `'static` | Dioxus component model | Dioxus leakage | Follows from #1 and #9. |
| 3 | Props must be `PartialEq`, and equality drives re-rendering | Dioxus memoization | Dioxus leakage | Outou has not defined its own update semantics yet. |
| 4 | `Element = Option<VNode>` | Dioxus core | Dioxus leakage | Outou exposes the name `Element` only. Whether it stays an `Option` is a runtime decision. |
| 5 | The type of `children` is Dioxus's `Element` | Dioxus | Dioxus leakage | Same as #4. |

| 7 | `rsx!` is re-exported through `outou::__private` and appears in generated code | Codegen | Temporary limitation | Hidden path; never written by users. Appearing in a user-facing diagnostic is a Phase 0 failure. |

| 11 | Macro expansion names in scope: the backend's macros expand to unhygienic paths, so `outou::prelude` must also bring `dioxus_core`, `dioxus_elements`, `dioxus_signals` and `Props` into scope (hidden from docs) | Dioxus macro hygiene | Dioxus leakage | Discovered while building the facade. | 12 | Element and attribute vocabulary (`div`, `class`, …) is validated by the Dioxus HTML crate | Dioxus HTML crate | Temporary limitation | An unknown attribute produces a Dioxus error today. Outou must translate it (see [design.md](design.md)). |
| 13 | Generated Rust must live at a fixed `src/.generated/` path referenced with `#[path]`, not under Cargo's `OUT_DIR` via `include!()` | rust-analyzer (Week 1 spike, `spikes/rust-analyzer/`) | Temporary limitation | Measured directly: with the identical `rsx!`-macro-based generated code, `OUT_DIR` + `include!()` made rust-analyzer's completion return zero/`null` results inside the `rsx!` macro call and under incomplete/broken input (both work fine for the `#[path]` layout). Not a Dioxus constraint — reproduced with the backend's own macro either way; the difference is an observed rust-analyzer behaviour difference between an `include!()`-spliced file and an ordinary `#[path]` source file; the mechanism was not investigated. | 14 | Attribute keys that are not a plain Rust identifier (hyphenated — `data-id` — or a Rust keyword — `type`, `for`, …; both legal per grammar §5) are emitted with Dioxus's raw string-key attribute syntax (`"data-id": value`) instead of `name: value` | Dioxus `rsx!` macro | Dioxus leakage | `crates/outou-backend-dioxus/src/escape.rs`, `is_plain_ident`. The JSX name itself is Outou intrinsic; the specific workaround syntax for writing it as a field key is Dioxus's. |
| 15 | Attribute and text string values are lowered into Dioxus's own format-string literals (`rsx!`'s ifmt), so a literal `{`/`}` byte in the value must be doubled to `{{`/`}}` before it is safe to splice | Dioxus `rsx!` macro (ifmt) | Dioxus leakage | `crates/outou-backend-dioxus/src/escape.rs`, `rust_string_literal`. Not observable through Outou's own grammar today — a raw `{`/`}` cannot appear inside `JsxText`, since `{` always opens an island (grammar §6) — but constrains codegen's implementation, and would surface immediately if that grammar rule ever changed. |
| 16 | Row 11's `TODO(phase0)` is resolved: codegen cannot emit fully qualified paths (`::dioxus_core::…`) instead of re-exporting `dioxus_core`/`dioxus_elements`/`dioxus_signals`/`Props` into `outou::prelude` | Dioxus `rsx!`/`#[component]` macro expansion | Dioxus leakage | Confirmed by reading the vendored `dioxus-rsx 0.7.10` and `dioxus-core-macro 0.7.10` sources (`~/.cargo/registry/src/*/dioxus-rsx-0.7.10/src/{element,component,template_body}.rs`): every expansion emits bare paths (`dioxus_core::TemplateNode::…`, `dioxus_elements::#i::#name`, `dioxus_core::Properties`, `dioxus_signals::GlobalSignal`), never `::`-prefixed ones, so these names must be in scope wherever `rsx!`/`#[component]` is invoked — i.e. in the user's own generated file, which only imports `use outou::prelude::*;`. Row 11's re-exports (already present in `crates/outou/src/lib.rs`) remain necessary; this row records that the alternative was investigated and rejected, not silently dropped. |
| 17 | Correction to row 14: its raw string-key attribute syntax (`"name": value`) exists only for **elements**. | 18 | A hyphenated JSX attribute name (`data-id`) is unrepresentable on a **component**: it is not a legal plain identifier, and `-` makes it illegal as a raw identifier too (`r#data-id` does not parse), so there is no Rust field-key spelling for it in a derived Props struct at all | Rust identifier grammar, via Dioxus's derived `Props` struct | Dioxus leakage | Issue #6, HIGH-3. No fix applied in issue #6; recorded per the fix list's decision to defer it. |
| 19 | rustc diagnostics for generated code render Dioxus's own type paths and `PropsBuilder` machinery directly to the user, not just backend vocabulary in prose | Dioxus component model (`#[component]`/`Props` derive) surfacing through `rustc`'s own path-printing and deprecation lints | Dioxus leakage | Issue #6, HIGH-6. `#[doc(hidden)]` is rustdoc-only and does not change how `rustc` prints a path; `outou::prelude::dioxus_core` is a genuinely public path and the shortest one available, so rustc chooses it. Reproduced in a plain user crate: a non-`IntoDynNode` island child gives `` the trait bound i32: IntoDynNode<outou::prelude::dioxus_core::nodes::FromNodeIterator> is not satisfied ``; a missing required prop gives `` warning: use of deprecated method `GreetingPropsBuilder::<((),)>::build`: Missing required field name `` together with `` argument #1 of type `GreetingPropsBuilder_Error_Missing_required_field_name` is missing `` and `` this error originates in the derive macro `Props` ``. Not fixable by removing the re-export (rustc would print `dioxus_core::…` instead); inherent to using Dioxus as a backend. Row 11 records only that the names are visible to completion; row 16 records only that qualified paths are impossible. Neither records diagnostics rendering them, which is the more consequential fact. |
| 20 | A non-`String`/`&str`/`Element`/iterator island child does not compile: Dioxus requires a child's type to implement `IntoDynNode` | Dioxus core (`IntoDynNode`) | Temporary limitation | Issue #6, HIGH-7. `<p>{n}</p>` with `n: i32` fails with `error[E0277]: the trait bound i32: IntoDynNode<…> is not satisfied`; `{n.to_string()}` compiles. React allows a bare number (or `null`/`bool`, which React renders as nothing) as a child; Outou does not yet translate this restriction into an Outou diagnostic. Row 12 covers element/attribute vocabulary, not island child types. |
| 21 | An island attribute value (`attr={expr}`) is always wrapped in braces when lowered (`attr: {expr}`), which trips Rust's own `unused_braces` lint in the user's build (`<div tabindex={1}>`, `onclick={move \|_\| …}`, …), pointing into `src/.generated/` | Codegen (`crates/outou-backend-dioxus/src/element.rs`, `lower_island`) | Temporary limitation | Issue #6, MEDIUM-12. Not universally strippable: dropping the braces breaks a nested-`rsx!` island prop (`icon={<span/>}` needs them — `error: expected identifier` without); replacing them with parens produces `unused_parens` instead. A `-D warnings` user's build fails on this today. No fix applied in issue #6 (no clean universal fix exists); deferred to issue #8. |
| 22 | Correction to row 15: a literal `{`/`}` byte **is** observable through Outou's own grammar today, in an attribute string value — `class="a{b}c"` is legal Outou and hits exactly the ifmt-escaping row 15 describes. Only the `JsxText` (element child text) half of row 15's claim holds, since `{` always opens an island there (grammar §6) | (documentation correction; no code change) | Dioxus leakage | Issue #6, LOW-16. | 23 | Correction and narrowing to row 21: an island attribute value only needs its braces when it is *not* a single, statement-free Rust expression — `<div tabindex={x}>`, `onclick={move \|_\| { .. }}`, `s={S { a: 1 }}` and `tabindex={if c { 1 } else { 2 }}` all lower brace-less (`tabindex: x`, …) and never trip `unused_braces`; only a nested-JSX island prop (`icon={<span/>}`) still needs them, and only a file containing at least one such prop now carries `#![allow(unused_braces)]` at all. | 24 | The language server (`crates/outou-lsp`) forwards rustc/rust-analyzer diagnostic messages for generated code largely verbatim; only a small, explicit table (`crates/outou-lsp/src/translate.rs`) rewrites a message that still contains a backend marker after mapping | Dioxus component model, surfacing through rustc's own diagnostics (same root cause as row 19), now also reaching the user through the IDE, not only `cargo build` | Dioxus leakage / Temporary limitation | Issue #9, Gate 3. The table checks for `rsx!`, `PropsBuilder`, `dioxus_rsx`, `GeneratedNode`, `IntoDynNode` and the `dioxus_core`/`dioxus_elements`/`dioxus_signals` module paths; a message containing one gets either a specific rewrite (`PropsBuilder` → "this component is missing a required property") or a generic one ("the backend rejected this element; see the generated code"), with the original text preserved in the diagnostic's `data` field rather than shown by default. No message observed during Gate 3's own probes (`docs/gate3-results.md`) actually contained a marker — every diagnostic seen there (`mismatched types`, `E0599` method-not-found, native syntax errors) was already in Outou vocabulary — so this row records the mechanism, not a new reproduction; row 19 already documents that rustc *can* print Dioxus paths directly (a missing required prop, a non-`IntoDynNode` child), and this table is what the LSP applies when that happens through the IDE rather than `cargo build`'s own terminal output (which this table does not touch — `outou-cli` never runs it). |
| 25 | Row 24's own mechanism was incomplete: `Diagnostic.data` (populated with the untranslated original message), `relatedInformation` locations/messages, and every field of a `textDocument/completion` item (`label`, `detail`, `documentation`, `filterText`) were none of them sanitized — only the top-level diagnostic `message` was. Live reproductions: hovering an HTML element returned `dioxus_html::elements`/`use dioxus::prelude::*;` verbatim; `<UserC` (a generic identifier-completion position, not a props/tag position at all) returned 155 items including `__TEMPLATE_ROOTS`, `GreetingPropsBuilder_Error_Missing_required_field_name` and `App_completions::`; `<div class=` returned `dioxus_core::`/`dioxus_elements::`/`dioxus_signals::` as completion *labels*, at a wrongly-mapped zero-width edit position that would corrupt the buffer if accepted | Dioxus component model / macro expansion, surfacing through rustc's diagnostic `data`/`relatedInformation` fields and rust-analyzer's raw (unmapped, unfiltered) completion results for generated Rust | Dioxus leakage | Issue #9, Gate 3 review (M4/HIGH-9). Fixed in `crates/outou-lsp/src/{translate,response,diagnostics}.rs`: `Diagnostic.data` is now always cleared rather than populated; `relatedInformation` locations are recursively reverse-mapped (an unmapped entry is dropped, not shown pointing at `src/.generated/…`) and its messages translated; every completion item is filtered by an extended `BACKEND_MARKERS` list (adding `dioxus_html`, `VNode`, `RenderError`, `Properties`, `__template`, `_completions`, `typed_builder`) plus a `^__`/`Props$` shape check, with `documentation` stripped from every surviving item and any item whose primary edit range does not contain the request cursor dropped outright (this also fixes the `<div class=` corruption, independent of the leakage itself); hover `contents` has `::outou::__private::`/`dioxus_*::` path prefixes stripped and any surviving line still naming a marker removed, dropping the whole hover if nothing is left. Root cause for the *component* identifier leak (`<UserC` returning generic Rust-identifier completions, not a props/tag-name answer) is separate and recorded as a **Temporary limitation** by row 26, not this row. |
| 26 | Component and HTML tag/attribute name completion cannot be answered correctly by forwarding to rust-analyzer at all, at any position, no matter how well the response is sanitized: rust-analyzer only ever sees the *expanded* Rust, where a JSX tag name is indistinguishable from an ordinary struct-literal identifier position (`<UserC` returned an ordinary "identifier in scope" completion — `UserCard` present only as one of 155 unrelated items — never a props/tag-name-shaped answer) | Codegen's own lowering (`rsx!`/typed-builder expansion) erases the tag-name/attribute-name distinction that exists in `.rsx` before generation | Temporary limitation | Issue #9, Gate 3 review (M3/HIGH-7/HIGH-10). Fixed by *not* forwarding these two positions to rust-analyzer at all: `crates/outou-lsp/src/complete.rs` classifies the `.rsx` cursor against Outou's own (recovery) parse tree and answers `TagName`/`AttrName` positions locally from the plan's `#[component]` functions and a static HTML element list — deterministic, leak-free by construction, and not dependent on sanitizing a backend answer after the fact. `docs/gate3-results.md`'s previous "known limitation" claiming `<UserCard us` (an attribute name on an unclosed tag) does not reach rust-analyzer as a props-builder context was itself factually wrong — it does, and used to work — but is now moot: that position is answered locally instead, never forwarded. |
| 27 | A missing required prop on a component produces *two* separate rustc diagnostics for one `.rsx` mistake, not one: row 19/24's already-translated deprecated-`build`-method warning, **and** a second, distinct error — `` this method takes 1 argument but 0 arguments were supplied `` — pointing at the same call, which names no `BACKEND_MARKERS` substring at all and so passes through `outou_syntax::vocabulary::translate_message` completely untouched | Dioxus's derived `Props` builder (`typed_builder`-style `.build()` requiring a placeholder tuple argument even when every field is "missing") | Dioxus leakage | Issue #11. Reproduced building `tests/ui/backend-missing-required-prop/input.rsx` (`<UserCard />` with a missing required `name` prop): `cargo check --message-format=json` emits, in order, `` warning: use of deprecated method `UserCardPropsBuilder::<((),)>::build`: Missing required field name `` (translated per row 19's rewrite) and `` error: this method takes 1 argument but 0 arguments were supplied `` (left exactly as rustc wrote it). The second message is arguably still backend-shaped — an ordinary Rust user would never see a `.build()` call with a wrong argument count from code they wrote themselves — but it is not literally backend vocabulary by this table's substring rule, so `crates/outou-cli/tests/leak.rs`'s leak scan does not flag it and `translate_message` applies no rewrite. Recorded as a known gap in the translation table's coverage rather than fixed here: catching a marker-less message would need a smarter rule than substring matching (e.g. "the second diagnostic at the same span as a translated one"), out of scope for issue #11 to design. |
| 28 | Row 27's gap is closed, cheaply, without a general "smarter than substring" classifier: an untranslated diagnostic whose *mapped span* exactly matches a diagnostic that *was* translated is dropped from the rendered output, keeping only the translated one | Same as row 27 | Dioxus leakage (fixed) | Issue #12 corpus review, F21. `crates/outou-cli/tests/ui.rs`'s `suppress_untranslated_duplicates` implements this in the harness's render path (~15 lines); `tests/ui/backend-missing-required-prop/expected.stderr` now shows only the translated warning. Narrow by design — it only ever removes an untranslated diagnostic that shares a span with a translated one, never a diagnostic at a span nothing else maps to, so a genuinely independent untranslated message is still shown (and still a tracked gap if it happens to be backend-shaped in substance without sharing a span with a translated sibling). |

Rows are appended, never rewritten, as new leakage is found. The runtime decision after Phase 0 counts how many rows make Outou semantics unnatural and weighs that against interop freedom, renderer control, performance, bundle size, API stability and upgrade cost.
