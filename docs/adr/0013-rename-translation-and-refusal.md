# 0013. Rename/references translation and the refusal policy

Status: Accepted

## Context

`textDocument/rename` and `textDocument/references` are forwarded to rust-analyzer against the generated Rust file, the same pattern hover/definition/completion already use. The results, though, are not single positions: a rename returns a `WorkspaceEdit` (potentially touching several files), and both features must decide what to do when part of the answer lands in generated code with no corresponding `.rsx` source at all, and how to keep a JSX element's opening and closing tag in sync from one rename.

## Decision

**Both tags update for free, via the existing many-to-many map.** ADR 0007 already records that a JSX element's generated identifier is written once but mapped from *both* its opening and closing tag spans (`outou-backend-dioxus`'s `lower_element_body`). Reverse-mapping one generated edit or reference through `outou_sourcemap::Registry::reverse` (already used for diagnostics and hover) therefore yields both `.rsx` spans directly — there is no separate step that "also edits the closing tag," and so no way for that step to be forgotten or to drift out of sync with the source map's own model.

**Path-qualified component names need no special handling.** `docs/grammar.md` §5 requires a component tag name to be a plain Rust `IDENTIFIER`; `<ui::Button>` is not valid Outou JSX syntax. A JSX tag's own identifier span can therefore never contain `::`, so "rename `ui::Button`, only the last segment changes" cannot arise through a JSX tag occurrence under the current grammar. A rename that also touches an ordinary `.rs` position (e.g. a `use ui::Button;` import) passes through unchanged, exactly like any other non-generated location — rust-analyzer already computes the correct edit there, in Rust terms, and Outou has nothing to add.

**Rename refuses rather than partially applies.** An edit that lands inside a *known generated file* but maps to no source at all (synthesized code: a recovery placeholder, or the `rsx!` macro's own punctuation) is not silently dropped. The whole rename is refused, as an LSP error response in Outou vocabulary, because a rename that silently skips one occurrence while renaming the rest leaves the crate in a state that no longer compiles, or renames only part of what the user asked for with no visible sign that anything was left out. A resource operation (create/rename/delete a file) that names a generated file is refused for the same reason: there is no sound `.rsx` translation of a file-level operation on code Outou generates.

**References drops, rename refuses.** `textDocument/references` is read-only: an unmappable location is simply omitted from the result. There is no equivalent risk of leaving the workspace in a half-changed state, so the stricter refusal policy would only cost the user a result for no safety benefit.

**Versioned identifiers.** In a `WorkspaceEdit`'s `documentChanges` form, a translated `.rsx` entry's `textDocument.version` is always the `.rsx` document's own **current** version (`Workspace::rsx`'s tracked version) at the moment the edit is sent to the editor, never the generated file's version rust-analyzer originally used. An untouched ordinary `.rs` entry keeps whatever identifier rust-analyzer already gave it.

This alone does **not** protect against a stale edit: stamping with the current version only tells the client which version to apply *against*, it does not verify that rust-analyzer's answer was computed against text the request was actually sent for. An ordinary `didChange` regeneration (as opposed to a crate-wide re-plan) does not change anything this server's own epoch tracking (issue #9 Gate 3 review, S3) would catch, since it bumps neither the epoch nor invalidates in-flight requests — so a document edited *after* a rename request was forwarded but *before* rust-analyzer answered would otherwise be silently translated against the new text and stamped with the new version, misplacing or corrupting the edit. `Pending` (`crate::dispatch`) therefore also records the `.rsx` document's version at the moment of forwarding for rename, prepareRename, references and semantic tokens; a response whose document version no longer matches is refused (`ContentModified`, `-32801`) rather than translated — `prepareRename` alone answers `null`, since failing loudly for what is usually just a fast typist winning a race is worse than silently not offering a rename that keystroke.

**De-duplication.** Two rust-analyzer edits (or references) that reverse-map onto the same exact `.rsx` `(uri, range, newText)` triple collapse to one; applying the same edit twice would corrupt the buffer.

## Consequences

- Rename and references share one translation primitive (`crate::mapping::generated_range_to_all_sources`), extending the hover/definition/completion machinery rather than duplicating it (`AGENTS.md`'s "there is one compiler" spirit, applied to this server's own position translation).
- **Whole-span reverse mapping (`outou_sourcemap::Registry::reverse`/`SourceMap::map_range`) is unsound for an edit and must never be used for one.** An earlier version of this translation primitive used `Registry::reverse` directly, which is designed for a diagnostic or "what does this span come from" query and deliberately returns a *containing* mapping's whole source span. Reproduced live against `examples/phase0-app`: renaming the component `Greeting` sent rust-analyzer an 8-byte generated identifier query that fell *inside* the 22-byte verbatim-copied `fn Greeting(x: i32) {}` mapping, and the whole-span answer replaced the entire signature with the new name — not a synthesized-code edge case, but the ordinary, ubiquitous case of an identifier inside a verbatim-copied item. `crate::mapping::generated_range_to_all_sources` is now built on `outou_sourcemap::SourceMap::narrow` (the same primitive hover/definition already used) precisely because it narrows to an offset-preserved sub-range instead of a whole containing span, and only ever returns a whole span when the query exactly equals a mapping's own generated span (the genuine N:M identifier-mapping case). Any future caller that needs "does this span come from `.rsx`" should keep using `reverse`/`map_range`; any caller producing an *edit* or a *location meant to be precise* must use `narrow`-based translation instead.
- A rename that lands on truly synthesized code (no source at all) still visibly fails, with an explanation the user can act on.
- If a future backend or grammar change ever allows a path-qualified component tag, this decision's "needs no special handling" reasoning would need revisiting; a `TODO(phase0)` is not added because the current grammar makes it unreachable, not merely deferred.
- The same length-mismatch refusal that makes rename/references sound also means a keyword-named prop (`type`, lowered to the raw identifier `r#type`) has **no** rename/references answer at all — refused/dropped exactly like synthesized code, even though its `.rsx` occurrence is a perfectly ordinary attribute name (`docs/backend-leakage.md` row 29). No text-only fallback is implemented for this specific, narrower shape (an attribute name whose generated form differs only by Rust's raw-identifier/hyphen escaping); `TODO(phase0)`.
- `prepareRename` on a *closing* tag's own name returns the *opening* tag's range, not the closing tag's (`crate::mapping::generated_location_to_source`'s multi-source rule always resolves to the first source, shared with hover/definition): the request is still forwarded and answered correctly in substance, but the highlighted range does not match where the cursor actually was. `TODO(phase0)` in `crate::rename::translate_prepare_rename_response`'s own doc comment.

## Alternatives considered

- **Apply what can be mapped, drop the rest silently.** Rejected: this is exactly the failure mode ("part of the rename lands nowhere, and nothing tells the user") the issue's own spec calls out as unacceptable for rename specifically.
- **Best-effort nearest-position fallback for unmappable rename edits** (mirroring `crate::mapping::nearest_source_position`, used for diagnostics). Rejected for rename: a diagnostic's approximate position is merely inconvenient; a rename edit applied at an approximate position could silently corrupt unrelated text.
- **Synthesize a closing-tag edit from the AST instead of relying on the source map's own multi-source mapping.** Considered and rejected once the mapping was inspected: `outou-backend-dioxus` already records both tag spans on the identifier's own mapping, so a second, AST-driven synthesis path would duplicate logic the source map already provides, with two ways for the two paths to disagree.
