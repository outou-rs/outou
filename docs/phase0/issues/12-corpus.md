- [x] `cargo xtask corpus fetch` reads `corpus.lock` and clones each entry at its pinned tag (or commit) into `.corpus/` — `xtask/src/corpus/{lock,fetch}.rs`. A shallow, cone-mode sparse checkout (`git clone --filter=blob:none --no-checkout --depth 1 --branch <tag>` + `sparse-checkout init --cone` + `sparse-checkout set <path>` + `checkout HEAD`) fetches only `path`; a `.outou-revision` marker skips a repeat fetch already at the right revision. Nothing is vendored into the repository (`.corpus/` stays gitignored). The marker's first line is the pinned revision; a second line records the commit the fetch actually resolved to, verified against `corpus.lock`'s own `verified_commit` field for a tag-pinned entry and failing loudly on a mismatch (issue #12 corpus review, F8: a retagged upstream must not silently change the corpus a `.lock` file exists to pin).
- [x] `cargo xtask corpus test` runs the parser over every file and reports: panics, files that fail to parse, files whose JSX-free round trip differs — `xtask/src/corpus/{test,splice,report}.rs`. Each file is parsed in a `catch_unwind` on its own thread with a 2s wall-clock budget (a hung parse is reported as a timeout, not joined). Since the corpus is plain Rust, an Outou diagnostic on it is a false positive (reported, not a failure), split by whether rustc itself also rejects the file and by severity (F6), and any JSX element found at all is by definition a mis-detection, reported separately from a genuine splice-partitioning bug rather than folded into one bucket (F7). A full summary, carrying the resolved revision and scan timestamp for provenance (F9), is written to `.corpus/report.json`, uploaded as a CI artifact, and also written to the nightly job's `$GITHUB_STEP_SUMMARY`; a truncated markdown summary prints to stdout. Only panics and timeouts fail the run by default; `--strict` also fails on false positives and JSX mis-detections/splice mismatches.
- [x] pin `corpus.lock` to a stable rust-lang/rust tag instead of a moving commit — pinned to tag `1.98.1` (the release matching the installed toolchain when this pin was chosen; its commit, `48a229ceaefd4985c50990b14116b6d856af0985`, is recorded as `verified_commit` and checked by every `corpus fetch`, not just written in a comment (F8)).
- [x] `.github/workflows/corpus.yml` becomes a real signal (remove `continue-on-error`) — removed; the nightly job now runs `corpus fetch` then `corpus test` (non-strict) and fails on a panic or timeout.
- [x] corpus categories from the test matrix covered: valid/invalid Rust, macro token trees, qualified paths, raw strings, lifetimes, generics — `corpus test` reports per-category file counts for `tests/ui/{macros,parser,generics,lifetimes}` plus `qualified paths` (filed under `fully-qualified-type` as of tag `1.98.1`) and two content-based categories, "valid Rust" (no `.stderr` companion) vs. "invalid Rust" (has one) and "raw strings" (a substring scan for `r"`/`r#`/`br`/`cr` forms). `crates/outou-syntax/tests/corpus_smoke.rs` adds in-repo snippets from the same categories (raw strings containing `<`/`>`, comparison chains, turbofish, HRTBs, a macro body containing literal `<div>` text, byte/char literals, lifetimes, nested generics, `<T as Trait>::f`/`::N`, plus the item-level whitespace-before-`<` shapes F1 below found) to the normal `cargo test --workspace` suite, asserting zero diagnostics and no JSX detected on all of them.

**Real run against tag `1.98.1`'s `tests/ui` (20,722 files, `.corpus` ~179 MB, commit `48a229ceaefd4985c50990b14116b6d856af0985`): 0 panics, 0 timeouts, 20 false positives (0.10% of files), 20 JSX mis-detections, 0 splice-partitioning mismatches.**

This corrects an earlier committed characterization of a since-fixed 61-file result, which described the false positives as "all pre-2018-syntax constructs such as `builtin-superkinds-*.rs`'s `BuiltinBounds`-style multi-bound lists and old-style associated-type paths" — a factually wrong root cause (issue #12 corpus review, F2: bound lists were never the mechanism; `trait B: A + Send {}` and `impl<T: Clone> …` both already parsed cleanly) that pointed Gate 4 at a "documented limitation of legacy syntax" instead of a fixable, current-Rust-affecting parser defect (F1).

**Root cause, found and fixed (F1, CRITICAL):** at item level (brace depth 0), `parser::item::parse_items`'s guard right after `scan_leading_attributes` reset the disambiguator's "previous significant token" context (`prev`) whenever *any* trivia was skipped — including plain whitespace with no attribute at all, and a comment with no attribute either — not only when an attribute or doc comment was actually consumed. With that context discarded, the classifier fell back to `position::from_prev(None)`'s permissive start-of-file default, and the very next `<` was misread as a JSX candidate. This affected ordinary, current Rust: `impl <T> Foo<T> {}`, `struct X <T> {}`, a top-level `const C: bool = A < B;`, `type Alias = Vec <u8>;`, and a type alias wrapped across lines before a `<`. Fixed by gating the reset on `!attrs.is_empty()` instead of `after_attrs > pos` (`crates/outou-syntax/src/parser/item.rs`), plus the same fix for the comment-skipping branch in both `parser::item` and `parser::region` (a comment, like whitespace, was also overwriting `prev` with itself rather than leaving the last real token's context intact). End-to-end regression tests, through the real `outou_syntax::parse` driver rather than the classifier functions in isolation (the gap that let this survive every existing unit test — F11), live in `crates/outou-syntax/tests/item_level_less_than.rs`.

**Breakdown of the remaining 20 (all rustc error-recovery/invalid-input fixtures, none affecting ordinary Rust):**

| Group | Count | Cause | Verdict |
|---|---|---|---|
| `tests/ui/parser/diff-markers/*.rs` — literal, unresolved `<<<<<<< HEAD` / `=======` / `>>>>>>>` merge-conflict markers | 13 | The catch-all JSX-candidate rule commits on `<` followed by an identifier-shaped token (`HEAD`); this is not valid Rust to begin with | Working as intended: only appears in an actually-broken merge; documented residual, not fixed |
| Malformed-operator / parser-torture fixtures deliberately testing rustc's own error recovery (`eq-less-to-less-eq.rs`'s `a =< b`, `range-exclusive-dotdotlt.rs`'s `0..<foo`, `unmatched-langle-2.rs`, `type-ascription-instead-of-path-2.rs`) | 4 | The permissive `Punct`-position default, on input no real program contains | Working as designed on deliberately invalid Rust |
| Bare `:` before `<` (`triple-colon.rs`'s `:::std:::`, `issues/issue-57819.rs`) | 2 | The documented D2/H4 residual risk (`:` is deliberately not a type-only position — see `lexer/position.rs`'s own doc comment) | Already documented; accepted trade-off |
| Bare `<>` immediately after a doc comment (`parser/doc-before-syntax-error.rs`) | 1 | Arguably spec-correct per grammar §4's "reserved, diagnosed" fragment rule | No action |

So the honest Gate 4 number is **20 false positives (0.10%)**, of which 13 are merge-conflict markers and 7 are rustc's own error-recovery/invalid-syntax torture fixtures — real residual risk on **zero** files of ordinary, valid Rust out of 20,722. See `.corpus/report.json` (not committed) for the full file list and per-file diagnostics after running `cargo xtask corpus fetch && cargo xtask corpus test`.

**Note on `cargo xtask corpus fetch` performance:** a plain (non-cone) `sparse-checkout set` combined with `--filter=blob:none`, or a cone-mode sparse checkout followed by `git checkout HEAD -- .` (an explicit `.` pathspec instead of a bare `checkout HEAD`), both fetch missing blobs one at a time against this corpus and did not finish inside 10 minutes in testing. `sparse-checkout init --cone` followed by a pathspec-free `checkout HEAD` fetches the sparse tree's blobs as one batch and finished in ~11s; see the comment in `xtask/src/corpus/fetch.rs::clone_sparse` for the measurements. The issue's documented ">10 min, fall back to a plainer `--depth 1` clone without the blob filter" path was evaluated but is not needed with this sequence.
